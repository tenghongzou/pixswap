# pixswap UX 設計規格

> 範圍：結構、流程、文案、無障礙。顏色、字體、間距數值、圖示風格由 UI 設計師負責，本文件不做規定。
> 基準程式碼：`src/pages/index.tsx`、`src/components/ImageConverter.tsx`、`src/styles/globals.css`（2026-09 版本）。

---

## 0. 現況盤點（設計出發點）

| 現況 | 對使用者的影響 |
| --- | --- |
| 首頁只有「Image Tools」和兩個連結 | 首頁不能直接轉檔，要多點一次；品牌名稱不一致 |
| 原生 `<input type=file>`，`accept` 限定單一 MIME | 無法拖放、貼上；丟錯格式時選檔對話框裡根本看不到檔案，使用者以為檔案不見了 |
| 選檔後要再按「轉換為 X」 | 多一步，而且大多數情況使用者沒有設定可以調 |
| `Promise.all` 一起轉換 | 任一檔失敗，整批結果都拿不到；大批檔案同時解碼容易吃光記憶體（手機尤其明顯）；沒有逐檔進度 |
| 結果只有轉換後的大小 | 看不出變大還是變小（JPG 轉 PNG 通常會大好幾倍，使用者會以為出錯了） |
| 沒有全部下載 | 20 張要點 20 次 |
| 只有一句隱私提示 | 核心賣點不夠顯眼，也沒說清楚「為什麼可以相信」 |

## 1. 目標使用者與主要情境

### 情境 A：簡報設計師壓圖（批次、桌機）
- **人物**：小林，品牌設計師，用 MacBook。
- **任務**：從 Figma 匯出了 18 張 PNG 截圖，每張 2–4 MB，放進 Keynote 後簡報檔超過 100 MB，Email 寄不出去。要把它們全部轉成 JPG，品質大約 80。
- **在意**：一次拖進去、一次全部拿回來；看得到每張省了多少；客戶的設計稿**不能上傳到第三方網站**（公司規定）。
- **設計重點**：拖放、批次、品質滑桿、大小前後比較、全部下載、明確的隱私說明。

### 情境 B：一般使用者要交件（單張、手機）
- **人物**：陳媽媽，用 iPhone。
- **任務**：區公所線上申請要上傳照片，網站只收 JPG，但她手上的檔案是 PNG（朋友用 LINE 傳來的截圖、或從網站存下來的圖）。她 Google「png 轉 jpg」點進來。
- **在意**：看得懂、按鈕大、不用註冊、存得回相簿或「檔案」。
- **設計重點**：搜尋落地頁 `/png-to-jpg` 一進來就能用；手機上的主要動作是一顆大按鈕「選擇圖片」；轉完直接出現下載按鈕，不需要再調設定。

### 情境 C：工程師要透明圖（貼上、桌機）
- **人物**：阿哲，前端工程師。
- **任務**：截了一張畫面（剪貼簿裡是圖片），或是手上有一張 JPG logo，要轉成 PNG 放進 repo。
- **在意**：快。最好 Ctrl+V 就轉好，下載檔名合理。
- **設計重點**：頁面上任何位置都能 Ctrl/⌘+V 貼上；貼上的圖給有意義的檔名；提醒「JPG 轉 PNG 不會自動去背」，免得預期落差。

## 2. 資訊架構

### 2.1 選項比較

| 方案 | 優點 | 缺點 |
| --- | --- | --- |
| **A. 維持一格式配對一頁**（現況） | 每頁都有獨立 `<title>`、`<h1>`、描述，對「png 轉 jpg」這類長尾搜尋最有利；靜態匯出很自然 | 首頁不能直接用；配對一多，頁面檔案跟著變多 |
| **B. 單頁 + 「來源 → 目標」選擇器** | 一個入口，操作最直覺；程式最少 | 只有一個 URL，搜尋落地頁價值幾乎歸零；用 query string（`?from=png&to=jpg`）在靜態匯出下無法產生不同的 meta，搜尋引擎也不會當成獨立頁面 |
| **C. 混合（建議）** | 兼顧 SEO 與首頁可直接使用 | 需要一份共用的配對設定檔 |

### 2.2 建議：方案 C（混合）

```
/pixswap/                 首頁：萬用轉換器（接受任何瀏覽器能解碼的圖片，選擇輸出格式）
/pixswap/jpg-to-png/      落地頁：預設輸出 PNG，標題與說明針對 JPG→PNG
/pixswap/png-to-jpg/      落地頁：預設輸出 JPG，標題與說明針對 PNG→JPG
（Later）/pixswap/webp-to-jpg/、/png-to-webp/ …   由同一份設定檔產生
```

1. **首頁就是轉換器**：有「輸出格式」選擇器（MVP 只有 PNG / JPG 兩個選項），下方列出「常用轉換」連結到各落地頁（同時是給搜尋引擎的內部連結）。
2. **落地頁共用同一個轉換元件**，差別只有：預設輸出格式、`<title>`、`<meta description>`、`<h1>`、一小段該配對專屬的說明（例如 PNG→JPG 會說「透明區域會填成白色」）。
3. **落地頁不放輸出格式選擇器**，改放一個反向連結「要反過來轉？PNG 轉 JPG →」。理由：在落地頁切換格式會讓 URL、`<h1>` 跟實際行為不一致；而不同頁面檔案之間跳轉，Pages Router 會重新掛載元件，已選的檔案會消失，這種體驗比沒有選擇器更糟。
4. **路由實作建議**：MVP 維持兩個實體頁面檔即可（最少變動）。配對超過 3 組時，改成 `src/pages/[pair].tsx` + `getStaticPaths`（`fallback: false`），從一份 `formats` 設定陣列產生，靜態匯出可支援。
5. **靜態匯出與子路徑注意事項**（給工程師）：
   - 站內連結一律用 `next/link`，讓 `basePath` 自動補上 `/pixswap`，不要手寫 `/jpg-to-png`。
   - 建議開啟 `trailingSlash: true`，讓 GitHub Pages 以 `jpg-to-png/index.html` 提供頁面，避免重新整理時出現 404。
   - 每頁都要有 `canonical` 指向完整網址 `https://tenghongzou.github.io/pixswap/<slug>/`。
   - 需要一個 `404.html`，放一個連回首頁的連結。

### 2.3 「來源格式」的處理原則

- **不限制來源格式**：`accept="image/*"`。只要瀏覽器能用 `createImageBitmap` 解碼就轉（JPG、PNG、WebP、GIF 第一格、BMP，AVIF／HEIC 視瀏覽器而定）。落地頁 `/png-to-jpg` 收到 WebP 也照樣轉成 JPG，不擋使用者。
- **來源與目標格式相同**（例如在 `/jpg-to-png` 丟進一張 PNG）：這一項標成「略過」，不轉換，並附上一個「仍要重新輸出」的次要動作（可以拿來用新的品質重新壓縮 JPG）。
- **不是圖片或無法解碼**（PDF、HEIC 在 Chrome 上等）：這一項標成「失敗」，給出可以照著做的建議（見 §5 錯誤訊息）。

## 3. 核心流程

### 3.1 總覽

```
進入頁面
  │
  ├─ 選檔（點按鈕 / 拖放 / Ctrl+V 貼上）──┐
  │                                        ▼
  │                              加入佇列，立即自動開始轉換
  │                                        │
  │         （可隨時再加檔：新檔排在佇列後面，已完成的保留）
  │                                        ▼
  │                              逐檔顯示：等待中 → 轉換中 → 完成 / 失敗 / 略過
  │                                        ▼
  │                              全部結束 → 播報摘要 → 下載（單檔 / 全部）
  │                                        ▼
  └────────────────────────────── 清除全部 → 回到空狀態
```

### 3.2 決策：自動開始，不用按鈕觸發

- 大多數使用者沒有設定要改，「選檔 → 按轉換」的第二步純粹是阻力。轉換在本機進行，免費且可以重來，自動開始沒有風險。
- **設定放在選檔區上方**，讓想調整的人在丟檔前就看得到（情境 A 會先把品質拉到 80 再丟檔）。
- **轉換後才改設定**（例如改了品質）：不自動重跑整批（大批檔案會卡），改在結果區頂部出現提示列「設定已變更 · [用新設定重新轉換]」。按下後只重跑「完成」和「略過」的項目。
- 首頁在轉換後切換輸出格式也一樣：出現同樣的提示列，不自動重跑。

### 3.3 步驟與狀態

#### 步驟 1：選檔

輸入管道（三種都進同一個佇列）：
1. **點擊**：拖放區本身就是一顆 `<button>`（或包住隱藏 file input 的 `<label>`），文字「選擇圖片」。`multiple`，`accept="image/*"`。
2. **拖放**：在整個視窗接受 drop（不只是拖放區），避免使用者放歪了、瀏覽器直接開啟圖片而離開頁面。拖放區是視覺目標。
3. **貼上**：`document` 監聽 `paste`，取剪貼簿裡的圖片檔。焦點在文字輸入框（目前只有品質滑桿，不是文字框）時不攔截。

| 狀態 | 畫面 | 說明 |
| --- | --- | --- |
| **空** | 大拖放區：圖示 + 「拖曳圖片到這裡，或 [選擇圖片]」+ 次要文字「也可以直接貼上（Ctrl+V）」+ 隱私提示 | 手機版不提拖曳與 Ctrl+V，只顯示「選擇圖片」大按鈕 |
| **拖入中** | 使用者拖著檔案進入視窗時，拖放區進入強調狀態，文字換成「放開以加入圖片」 | 用 `dragenter`/`dragleave` 計數器避免閃爍；拖出視窗或按 Esc 取消時恢復原狀 |
| **拖入非圖片** | 拖入中無法事先判斷格式（瀏覽器限制），放開後才在該項顯示失敗 | 若整批都不是圖片：拖放區下方出現錯誤「這些檔案不是圖片，沒有加入」，不建立結果清單 |
| **已有結果時** | 拖放區縮成一條精簡列：「[＋ 加入更多圖片]　或拖曳 / 貼上」，結果清單成為主體 | 避免結果被推到畫面外 |

貼上的檔名：剪貼簿圖片通常叫 `image.png`，改成 `pasted-20260924-153012.png` 這種帶時間的名稱，同一批內不會重複。

同名處理：批次內輸出檔名重複時（例如 `a.png` 和 `a.jpg` 都要轉成 `a.jpg`），後者加上 `-2`、`-3`。

#### 步驟 2：設定

- **輸出格式**（只在首頁）：分段選擇「PNG ／ JPG」，是一組 radio，預設 JPG（壓縮是最常見的需求）。
- **品質**（輸出 JPG 時才出現）：滑桿 10–100，預設 **85**（目前是 92，對「壓小一點」的需求來說偏大；85 在大多數照片上肉眼幾乎分不出差異，檔案小很多）。滑桿旁顯示數值，兩端標註「檔案較小」和「畫質較好」。
- **配對專屬提示**（靜態文字，不是設定）：
  - 輸出 JPG：「JPG 不支援透明，透明區域會變成白色。」
  - 輸出 PNG：「PNG 是無損格式，由 JPG 轉過來的檔案通常會變大，畫質不會變好。」
- MVP **不做**：尺寸縮放、背景色選擇、保留 EXIF。

#### 步驟 3：轉換（處理中）

- **逐檔、依序處理**（同時最多 1–2 張），改用 `allSettled` 的精神：每一檔各自成功或失敗，不互相拖累。依序處理也讓手機記憶體撐得住，並且能顯示進度。
- 每一項的狀態：

| 項目狀態 | 顯示 |
| --- | --- |
| 等待中 | 檔名、原始大小、「等待中」 |
| 轉換中 | 檔名、原始大小、不確定型的進度指示（單張 Canvas 轉檔沒有進度可讀，不要假裝有百分比） |
| 完成 | 縮圖、輸出檔名、`原始大小 → 輸出大小（−62%）`、[下載] |
| 完成但變大 | 同上，差異顯示為「+140%」，並附一行說明「PNG 是無損格式，檔案變大是正常的」 |
| 略過 | 「已經是 PNG，不需要轉換」+ 次要動作 [仍要重新輸出] |
| 失敗 | 檔名、錯誤原因（白話）、[移除] |

- **整批進度**：結果區頂部摘要列「轉換中 3 / 18」，完成後變成「完成 17 張，1 張失敗 · 共省下 38.2 MB（−71%）」。
- 轉換中仍可繼續加檔、下載已完成的項目；「全部下載」在全部結束前為停用狀態，並顯示「轉換中…」。

#### 步驟 4：檢視與下載

| 整批狀態 | 摘要列 | 主要動作 |
| --- | --- | --- |
| **全部完成** | 「已完成 18 張 · 共 12.4 MB（原本 50.6 MB，−75%）」 | [全部下載（ZIP）]、[清除全部] |
| **部分失敗** | 「完成 17 張，1 張失敗」，失敗項排在清單最上面 | [下載 17 張（ZIP）]、[清除全部]；失敗項各自有 [移除] |
| **全部失敗** | 「沒有圖片轉換成功」+ 最常見的失敗原因 | [清除並重新選擇] |
| **只有 1 張** | 不顯示 ZIP，主要動作直接是 [下載 xxx.jpg] | 單檔不需要打包 |

縮圖：用輸出檔本身當縮圖，`alt` 為輸出檔名。點縮圖在新分頁開啟原尺寸（Later：燈箱比較前後）。

#### 全部下載：評估

| 做法 | 評估 |
| --- | --- |
| 連續觸發多個 `<a download>` | 不用寫程式，但 Chrome 會跳出「允許下載多個檔案」的權限詢問，Safari 和手機常常只下載第一個。**不建議當主要方案** |
| 引入 JSZip / fflate | 可靠，但違反「不加大型依賴」的原則（fflate 雖然小，仍是依賴） |
| **自己寫只儲存（STORE）不壓縮的 ZIP**（建議） | JPG/PNG 本身已經壓縮過，再 deflate 幾乎沒有效益，所以 ZIP 只需要「儲存」模式：本機檔頭 + 中央目錄 + CRC32，約 60–80 行、零依賴。檔名用 UTF-8 旗標（bit 11），中文檔名在 macOS / Windows 解壓才不會變亂碼 |
| File System Access API（`showDirectoryPicker`） | 只支援 Chromium 桌機，列為 Later 的漸進增強 |

- ZIP 檔名：`pixswap-{張數}張-{YYYYMMDD-HHmm}.zip`，例如 `pixswap-18張-20260924-1530.zip`。（若擔心非 ASCII 檔名在部分系統出問題，改用 `pixswap-18-images-20260924-1530.zip`，由工程師實測後決定。）
- 產生 ZIP 時按鈕顯示「打包中…」並停用，避免連點。
- 上限：總輸出超過約 500 MB 時，在按鈕旁提示「檔案很大，打包可能需要一點時間，手機可能無法完成」，但不阻擋。

#### 步驟 5：重新開始

- [清除全部]：清空佇列、釋放所有 object URL、回到空狀態，焦點移回「選擇圖片」按鈕。
- 不需要確認對話框：所有資料都還在使用者手上的原始檔，清掉沒有損失。但如果還有**未下載過**的完成項目，改用可復原的方式：清除後出現 5 秒的提示「已清除 18 張 · [復原]」。（MVP 可以先不做復原，直接清除。）
- 單項 [移除]：從清單移除並釋放該項 URL，焦點移到下一項的第一個按鈕；沒有下一項時移到上一項；清單空了就回到拖放區按鈕。

## 6. 無障礙

### 6.1 鍵盤操作

| 操作 | 行為 |
| --- | --- |
| Tab 順序 | 標題區連結 → 輸出格式（radio 群組）→ 品質滑桿 → 選擇圖片按鈕 → 摘要列動作（全部下載、清除全部）→ 各項目的 下載 / 移除 → 常用轉換連結 → 頁尾 |
| 輸出格式 | 原生 `<input type=radio>` 群組 + `<fieldset><legend>輸出格式</legend>`，方向鍵切換 |
| 品質滑桿 | 原生 `<input type=range>`，方向鍵 ±1、PageUp/PageDown ±10；`aria-valuetext="85，數值越高畫質越好、檔案越大"` |
| 選擇圖片 | Enter / Space 開啟檔案對話框 |
| 貼上 | 焦點在頁面任何位置（不在文字輸入框時）按 Ctrl/⌘+V 都能加入 |
| 拖入中 | Esc 取消拖曳時恢復原狀（瀏覽器原生行為，確保狀態有正確重設） |

- 不自訂快捷鍵（例如按 D 下載），避免和螢幕報讀器快捷鍵衝突。
- 所有可聚焦元素要有清楚可見的焦點樣式（視覺由 UI 定義，但**不能**移除 outline 而沒有替代）。

### 6.2 焦點管理

| 事件 | 焦點去向 |
| --- | --- |
| 選檔 / 拖放 / 貼上後 | **不移動**。使用者可能還要繼續加檔，結果由 aria-live 播報 |
| 全部轉換完成 | **不移動**（不搶焦點），只播報摘要 |
| 移除單項 | 下一項的第一個按鈕 → 沒有下一項就上一項 → 清單空了就回到「選擇圖片」 |
| 清除全部 | 「選擇圖片」按鈕 |
| 空狀態 → 有結果，拖放區縮成精簡版 | 如果焦點原本在大拖放區的按鈕上，要移到精簡版的「加入更多圖片」按鈕（同一個元素改樣式最簡單，焦點自然保留） |
| 按下「用新設定重新轉換」 | 焦點留在原處；按鈕消失時移到摘要列 |

### 6.3 aria-live 播報

- 摘要列用一個 `role="status"`（等於 `aria-live="polite"`）的元素，**只播報整批層級的變化**，不逐檔播報，避免 18 張圖片產生 54 則播報。
- 播報時機與內容：
  - 加入檔案：「已加入 18 張圖片，開始轉換」
  - 轉換中：不逐張播報。如果整批超過 10 秒還沒完成，每 10 秒最多播一次「轉換中 9 / 18」
  - 完成：「轉換完成：18 張成功，共省下 38.2 MB」
  - 部分失敗：「轉換完成：17 張成功，1 張失敗。失敗的項目列在清單最上方」
  - 清除：「已清除所有圖片」
- 非預期的全域錯誤（例如剪貼簿沒有圖片、瀏覽器不支援）用 `role="alert"`。
- 每一項的狀態文字（「轉換中…」、「完成」）放在項目內的可見文字裡，使用者用方向鍵瀏覽清單時就能讀到，不需要另外播報。
- 轉換中的進度指示圖示加 `aria-hidden="true"`，靠文字「轉換中…」表達。

### 6.4 拖放區的替代操作

- 拖放**永遠不是唯一**的輸入方式：拖放區裡一定有一顆真正的 `<button>`「選擇圖片」（或 `<label for>` 對應一個視覺隱藏但可聚焦的 file input）。不要把整個 `<div>` 加 `onClick` 當按鈕。
- 拖放區外框只是裝飾；螢幕報讀器使用者看到的是「選擇圖片，按鈕」加上一段說明（`aria-describedby` 指向「支援 JPG、PNG、WebP，可多選，也可以直接貼上」）。
- 貼上是給鍵盤使用者的另一條快速路徑，說明文字裡要寫出來。

### 6.5 其他

- 縮圖 `alt` 用輸出檔名；如果旁邊已經有同樣的檔名文字，改用 `alt=""` 避免重複朗讀。建議後者。
- 大小變化不要只靠顏色表達（變小綠、變大紅），要保留「−84%」、「+186%」的正負號文字。
- 轉換結果清單用 `<ul>`，讓報讀器可以讀出「清單，18 個項目」。
- 動作列按鈕在手機上的觸控目標至少 44×44 px。
- 若 UI 設計有拖入中的動畫或進度動畫，需尊重 `prefers-reduced-motion`。
- 頁面 `lang="zh-Hant"`。

## 7. 優先順序

### MVP（這一輪）

1. **更名為 pixswap**：首頁 h1、`<title>`、頁首品牌名稱。
2. **首頁直接可用**：首頁放轉換器 + 輸出格式選擇（PNG／JPG），下方保留「常用轉換」連結。
3. **落地頁保留** `/jpg-to-png`、`/png-to-jpg`，各自有 `<title>`、描述、h1、反向連結；確認 `basePath`、`trailingSlash`、canonical 正確。
4. **輸入**：拖放（整個視窗都能接收）、點選、Ctrl/⌘+V 貼上；`accept="image/*"`，不再用單一 MIME 擋檔。
5. **自動開始轉換**，逐檔依序處理，每檔獨立成功或失敗（取代 `Promise.all`）。
6. **逐檔狀態**：等待中／轉換中／完成／略過／失敗，並附白話錯誤訊息。
7. **大小比較**：原始 → 輸出（±%），整批摘要顯示總節省量。
8. **全部下載**：自寫 STORE 模式 ZIP（零依賴、UTF-8 檔名）；只有一張時直接下載該檔。
9. **清除全部**、單項移除，並正確釋放 object URL。
10. **隱私提示**強化：一行主要提示 + `<details>` 展開說明。
11. **手機版**：大按鈕選檔、底部固定動作列。
12. **無障礙**：真正的按鈕、`role="status"` 整批播報、焦點管理規則、fieldset/legend。
13. JPG 預設品質改為 85，品質滑桿加上兩端說明。

### Later

- **WebP 輸出**與更多落地頁（`/webp-to-jpg`、`/png-to-webp`…），改用 `[pair].tsx` + `getStaticPaths`。注意 Safari 的 `toBlob` 不支援 WebP 編碼，要先偵測，不支援時隱藏該選項。
- **設定變更後的「用新設定重新轉換」**：MVP 可以先簡化為「改設定只影響之後加入的檔案」，並在設定旁加一行說明。
- **清除後的「復原」**提示。
- **縮放尺寸**（最長邊 1920 / 自訂）：對「壓小給簡報用」的情境很有價值，但會增加設定複雜度。
- **透明偵測**：輸出 JPG 時只在來源確實有透明像素時才顯示白底提示，並提供背景色選擇。
- **前後比較燈箱**（左右拖曳比較品質）。
- **File System Access API**：Chromium 桌機可「儲存到資料夾」，免解壓縮。
- **Web Share API**：手機上「分享 / 存到相簿」，解決 iOS 下載進「檔案」App 的困擾。
- **PWA / 離線**：Service Worker 快取頁面，讓「關掉網路也能用」更完整。
- **Web Worker + OffscreenCanvas**：大批次時不卡住畫面。
- 多語系（英文版落地頁，SEO 價值高，但需要處理靜態匯出的 i18n 路由）。

### 明確不做

- 任何需要後端的功能（雲端儲存、分享連結、帳號）。
- 需要 WASM 編碼器的格式（AVIF 編碼、HEIC 編碼、mozjpeg 最佳化）：依賴太大，和專案規模不符。
